# List pages

- Pages that lists records should be navigable by the up and down button for selection
- Columns should be customizable via `ColumnsMenu` + `useColumnVisibility(key)` (`<ColumnsMenu columns={COLUMNS} {...columnMenu} />`). Every rendered column must be in `COLUMNS`. Toggling changes only the current view; **Save layout** stores it as the user's layout on the backend (`PUT /me/preferences/columns:<key>`, a JSON array of hidden keys; cached per user in localStorage so pages render before the fetch answers), **Revert to saved** and **Show all** reset it, and the button shows a dot while the view is unsaved
- Every list/report page has a Global Filter: the shared `GlobalSearch` component (`src/components/GlobalSearch.tsx`), placed **last** in the toolbar, wired as `<GlobalSearch value={search} onChange={setSearch} status={searchAll} />` with `searchAll` from `usePagedList`. It is deliberately a last resort: a small muted "Search all rows…" link (no hotkey) that expands into a search box, so users narrow with column filters first. It searches only on the frontend, across every field in the page's `searchText` (including user-hidden columns). A non-empty term puts `usePagedList` in search-all mode: it fetches **every** row matching the current column filters (refusing above `SEARCH_ALL_LIMIT` = 50000 and telling the user to narrow the column filters), filters them client-side, and rebuilds the pages and totals from the matches. Changing only the term reuses the fetched set; changing a column filter or Reload refetches it. Export applies the same term to its full filtered set
- The Column filters will query the backend for partial matching
- Date columns should be filterable by range. Add a utility for commonly used date ranges: Today, Current Week, Current Month, Last 30 Days, Last 3 Months, Current Year
- Transaction list pages and transaction reports (detailed reports, Inventory Ledger) open with their transaction-date column filtered to **Last 30 Days**: initialize the filters state with `useState(() => defaultDateFilter())` from `src/lib/dateRanges.ts` (pass the column key if it isn't `date`). Users can still change or clear it. A drill-down that hands over its own filters in the URL keeps them instead of the default. Master-data lists (`updatedAt` columns) stay unfiltered
- All lists should be by default paginated. Have 50 record per page as default. This should be supported by the backend. Users pick rows per page (25/50/100/200, max `MAX_VIEW_PAGE_SIZE` = 200) from the **Rows** selector in `Pagination`: wire it as `<Pagination … pageSize={pageSize} onPageChange={setPage} onPageSizeChange={setPageSize} />` with both values from `usePagedList`. The choice is saved per list/report page (`usePageSize`, `PUT /me/preferences/list.pageSize:<listKey>`, cached per user in localStorage); `<listKey>` is the endpoint path with `/` → `.` (e.g. `reports.detailed.purchase-orders`), or `usePagedList`'s `pageSizeKey` option when two pages share an endpoint, and changing it keeps the first visible row on screen. The 200 cap is for on-screen pages only; export and search-all still loop at the backend's 1000 max
- All list and report pages should be exportable to a spreadsheet. The columns exported should be based on the visible columns. Export covers **all rows matching the current column filters across every page**, not just the page on screen — export handlers call `fetchAllContent(endpoint + filters)`, which pages through the backend (capped at 1000 rows per request) until the last page. The spreadsheet mirrors the list as shown: rows come in the current sort order (the `sort` param), and handlers pass the page's `grouping` as `exportToXlsx(name, visibleColumns, rows, grouping)` so a grouped list exports with a `Label: value (count)` row per group (in on-screen group order, with its subtotals, nested rows as collapsible Excel outline levels). `total` columns are written as numbers (`#,##0.00` / quantity format) and a **Grand total** row closes the sheet, summed over the exported rows.
- Boolean columns should be filterable by True, False or non filtered
- All list and report pages have a **Reload** button (`src/components/ReloadButton.tsx`, placed just before `ColumnsMenu`, hotkey `R`) that calls `usePagedList`'s `reload()` — it re-queries the backend with the current page and column filters (the defaults if untouched), never resetting them. Pass the hook's `loading` (aliased `listLoading`, since pages already use `loading` for submit state) so the icon spins while the request runs.
- Every list/report table goes in `ScrollTable` (never a bare `<table>`, or added columns spill off the right edge) (`src/components/ScrollTable.tsx`), which scrolls both ways inside its own box with a sticky header (titles + filter row) and no cell wrapping. Pass `activeIndex` so arrow-key navigation keeps the selected row in view. It needs a height-bounded parent: page root `flex h-full flex-col gap-6` (record pages: `inRecordTab ? 'space-y-6' : 'flex h-full flex-col gap-6'`, so the record form keeps scrolling normally), `Card` and `CardContent` `flex min-h-0 flex-col`, with `Pagination` after the `ScrollTable`. The page title sits on its own row above the toolbar (header `flex flex-col gap-3`), so a long title never wraps against the controls. Toolbars use `flex-wrap` so filters drop to a further line instead of overflowing. Pin one identifying column (e.g. Item Name, Reference #) with `PINNED_TH`/`PINNED_TD`, plus `pinnedKey` on `ColumnFilterRow`. Rows then need `group`, `data-active={i === activeIndex || undefined}` and an explicit `bg-[hsl(var(--card))]` before their hover/active backgrounds. Tables without a row-actions column pass `actions={false}` to `ColumnFilterRow`. Long free-text cells (Notes, Remarks) are capped with `<div className="max-w-xs truncate" title=…>`.
- Every list/report page has **Group by** (`GroupByMenu` from `src/components/RowGrouping.tsx`, placed just after `ColumnsMenu`): the user checks one or more columns and rows nest into collapsible groups, outermost level first, in the order they were checked. Every level collapses on its own; Shift+click (or Shift+Enter) on a group header expands/collapses it together with every group nested in it, and the menu has Expand all / Collapse all / Clear grouping. Groups start collapsed and show their row count. The grouped columns are the user's preference for that page (`PUT /me/preferences/list.groupBy:<key>`, a JSON array of column keys outermost first, saved on every change like rows-per-page and cached per user in localStorage); which groups are expanded isn't saved. Wiring: `const grouping = useRowGrouping(COLUMNS, '<key>')` (the page's `useColumnVisibility` key) **before** `usePagedList`, pass it `all: grouping.active` (grouped, the hook loads every row matching the column filters and Global Filter onto one page, with the same `SEARCH_ALL_LIMIT` refusal as search-all, reported by `GroupByMenu` from the hook's `allRows`), then `const view = useGroupedRows(grouping, items, listRow)`, where `listRow` is the page's export-row mapper (one displayed value per column key, so a group reads exactly like its cells; date columns group by day). Pass `view` to `useListKeyboardNav` (↑↓ walk group headers too; Enter/→ expands, ← collapses or steps out to the parent group), render the body with `groupedRows(view, { activeIndex, onActivate: setActiveIndex }, (row, i) => <tr …/>)` instead of `items.map`, and give `Pagination` `summary={view.summary}` (it replaces the page controls while grouped). Columns that make no sense as groups (e.g. an image) set `groupable: false` on their `ColumnDef`.
- **Sorting**: list headers sort the list on click (ascending → descending → back to the default order) via `SortableTh` + `useListSort(COLUMNS)`. Unsorted, the backend's default applies: last updated first for master data, last posted (`createdAt`) first for transactions and the ledger. Sorting is server-side so it orders every page, the grouped/search-all full set and the export: pass `filters: sorting.apply(debouncedFilters)` to `usePagedList` and `filtersToQueryString(sorting.apply(debouncedFilters))` in Export, which adds `sort=<columnKey>,asc|desc`. A column opts in with `sortable: true` on its `ColumnDef`, and **only** for keys in the endpoint's backend `SORTABLE` whitelist (see `../Norbiz/docs/LIST_FILTERING.md` → Sorting; any other key is a 400) — never for values computed in Java (Total Amount, status, display names, SKU lists). Render each header as `<SortableTh sorting={sorting} column="key" className=…>Label</SortableTh>` (it falls back to a plain `<th>` for non-sortable columns). Inventory Balance is sortable in its current mode only. The sort isn't saved.
- **Totals**: amount and quantity columns set `total: 'currency' | 'quantity'` on their `ColumnDef` (never unit prices or percentages). Group headers then show each group's subtotal under those columns, and the table gets a sticky **Grand total** footer — `<GrandTotalRow columns={COLUMNS} isVisible={isVisible} totals={grandTotals} />` right after `</tbody>` — covering every row matching the filters, not just the page. Wire `usePagedList(…, { totals: true })` (the endpoint must support `totals=true`, see `../Norbiz/docs/LIST_FILTERING.md` → Totals), destructure `allItems` and `totals`, and `const grandTotals = useGrandTotals(COLUMNS, allItems, totals, listRow)`: while the full set is loaded (grouped or searching) the totals are summed from it so they follow the search term, otherwise they come from the backend. Group subtotals and client-side totals are summed from the displayed (`listRow`) values.
