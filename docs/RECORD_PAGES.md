# Record pages (CRUD page pattern)

Pages under `src/pages/` (e.g. `UsersPage.tsx`) follow a consistent CRUD shape worth reusing rather than reinventing:
- Local state for the list, plus `mode` (`'view' | 'create' | 'edit'`)/`activeItem` for one shared form that handles view, create, and edit (fields become read-only in `'view'` mode instead of using a separate detail view).
- **Records open in workspace tabs, not modals.** The same page component renders in two places: the module ("main") tab shows the list, and each open record gets its own tab at `<module>/<id>` or `<module>/new`, showing only the form. Wire it with `useRecordTab` (`src/components/RecordTab.tsx`):
  - `const inRecordTab = useIsRecordTab()` before `usePagedList`, and pass `enabled: !inRecordTab` so record tabs don't fetch the list.
  - `const rec = useRecordTab<T>({ mode, onOpen: { view: openView, edit: openEdit, create: openCreate }, onRequestClose: requestClose, fetchRecord: id => apiFetch<T>(\`/x/${id}\`) })` right after the `mode` state. `fetchRecord` is used only when the tab has no record in hand (a pasted URL, or a tab restored after a refresh — stored tabs deliberately drop the record snapshot so they refetch). `/items` and `/users` have no GET-by-id endpoint, so those pages find the row in `fetchAllContent`.
  - First line of each `open{View,Edit,Create}`: `if (!rec.isRecordTab) return rec.open('view', item)` (list tab → open/activate the tab); the rest of the function seeds the form as before, and `useRecordTab` calls it inside the record tab. Re-opening a record whose tab is already open just activates it — except the list's Edit on a tab sitting in view mode, which switches it to edit.
  - `rec.close()` replaces `setOpen(false)` (after save, or inside `requestClose`'s guarded callback). `reload()` from `usePagedList` is broadcast to every mounted list of that endpoint, so calling it from the record tab refreshes the list tab.
  - JSX: list header + `Card` wrapped in `{!inRecordTab && (<>…</>)}`; the form wrapped in `{inRecordTab && <RecordSheet title={tabTitle} status={rec.status} onRequestClose={requestClose} className="max-w-2xl">…</RecordSheet>}`. `RecordSheet` names the tab, shows loading/not-found states, and makes Esc close the tab (guarded). The action-button bar uses `className={RECORD_ACTIONS}` (sticky at the bottom of the tab).
  - Hotkeys/row navigation stay gated on `!inRecordTab && zone === 'content'`; `useContentFocus()` reports `'inactive'` for hidden tabs, so a background tab never reacts to keys.
  - Tabs: Alt+1…9 switches (Alt+1 = module tab), Alt+W / middle-click / × closes through the page's `requestClose` (so the dirty guard still applies); the strip's **Close all** button / Alt+Shift+W runs every record tab's `requestClose` in one batch (`requestCloseAllTabs`), and a dirty tab whose discard is declined stays open; closing returns to the previously active tab. Open tabs (and the module tab's location) persist in `sessionStorage` per user. State lives in `src/context/WorkspaceContext.tsx`, the tab strip and keep-alive panels in `src/components/WorkspaceTabs.tsx`. A module opts in by having `recordLabel` (singular noun) on its `navItems` entry.
  - Other small modals (Reset Password, Change Password, command palette, shortcuts help) are still `Dialog`s.
- List rendered as a plain `<table>` inside `Card`/`CardContent`, row click opens view mode, action buttons (`Eye`/`Pencil`/`Trash2` from `lucide-react`) are gated per-row by `hasPermission('CREATE_X' | 'UPDATE_X' | 'DELETE_X')`.
- Errors from `apiFetch` are caught and surfaced via `useToast()` (`src/context/ToastContext.tsx`), not thrown further.
- Delete uses a plain `window.confirm` before calling the API. Its catch toasts `deleteErrorMessage(err, 'Failed to delete <entity>.')` (`src/lib/api.ts`): when the record is still referenced elsewhere the backend returns 409 `code: "ENTITY_IN_USE"` with a "cannot be deleted because it is still used by …" message, and the helper shows that (and any other 4xx message) instead of the generic fallback. `apiFetch`/`apiUpload` throw `ApiError` (`status`, `code`, `details`, `traceId`); `isEntityInUse(err)` checks for that case.
- Every record form's `handleSubmit` confirms before calling the API too: `if (!window.confirm(mode === 'create' ? \`Create <entity> "${name}"?\` : \`Save changes to <entity> "${name}"?\`)) return`, placed after existing field validation (so a truly invalid submit still just toasts and returns, no confirm shown) but before `setLoading(true)`. Transaction pages (Purchase Order, Purchase Invoice, Inventory Adjustment — create-only, no name field) use a fixed message instead: `Post this <transaction>? This cannot be edited afterward — only voided.`, naming the immutability consequence rather than an identifier. Matches the existing Delete/Void `window.confirm` convention rather than introducing a new dialog component.
- Closing a record tab (Cancel/Close button, the tab's ×, Alt+W, Escape) is guarded by `useDirtyGuard` (`src/hooks/useDirtyGuard.ts`) — it only confirms ("Discard unsaved changes?") when the user actually changed something since the dialog opened, not on every close. Wire it as: call `markClean(snapshot)` at the end of every `open{View,Edit,Create}` function (right after the `setX(...)` calls that seed the form, using those same just-set values — state updates are async, so re-reading the state variables immediately after wouldn't see them yet), define `function requestClose() { guardedClose(snapshot, () => rec.close()) }`, then route every close path through it: pass it as `useRecordTab`'s `onRequestClose` and `RecordSheet`'s `onRequestClose`, and the Cancel/Close buttons' `onClick={requestClose}` (both, not just Cancel — routing Close through it too is harmless since view mode's fields never change, so it never actually prompts there). `snapshot` is whatever combination of the page's form state is relevant — most pages have one `form` object and can pass it directly or as `{ form, companyId }` when `companyId` is tracked separately (`BrandsPage`/`ItemCategoriesPage` use bare `name`/`companyId` instead of a `form` object — snapshot those directly); transaction pages (no `form` object, many individual `useState` fields) snapshot all of the create-relevant fields as one object. `markClean`/`guardedClose` JSON-diff the snapshot, so pass plain serializable values — a field holding a `Set` (tags, permissions, company assignments) is fine, `Set` gets special-cased into a sorted array before comparing; a field holding a `File` (image upload) doesn't serialize meaningfully, so pass a derived boolean (`hasFile: !!selectedFile`) instead of the `File` object itself. Not applied to `DocumentTemplateDesignerPage` — it's a full-screen designer with its own Save.
- Transaction forms' "Add Line" button (Purchase Order, Purchase Invoice, Inventory Adjustment) has a `Ctrl+Enter` shortcut, shown as a `<kbd>` hint next to the button label — wired via `onKeyDown` on the `<form>` itself (`if ((e.ctrlKey || e.metaKey) && e.key === 'Enter') { e.preventDefault(); addLine() }`), not `useHotkeys` (that hook is disabled while any dialog is open). Deliberately not plain `Enter` — that's already claimed by `SearchableSelect`'s "confirm field, advance to next" behavior and by native form submit-on-Enter. On `PurchaseInvoicesPage` the handler is additionally gated on `invoiceMode === 'DIRECT'` — PO-based mode's lines mirror the selected PO 1:1 and aren't user-extendable, so the same guard that hides the button there also has to gate the shortcut.
- Always show a user's **Display Name**, never their raw username, anywhere a form/list surfaces who did something. Every `Auditable` entity's `createdBy`/`updatedBy`/`voidedBy` is stamped by the backend's `AuditorAwareImpl` with the username (`Authentication.getName()`), not displayName — username is the correct stable key to persist, but the wrong thing to show. Resolve it client-side with `useUserDisplayNames` (`src/hooks/useUserDisplayNames.ts`): `const resolveDisplayName = useUserDisplayNames()`, then `resolveDisplayName(record.createdBy)` anywhere that field is rendered — detail-view "Created by"/"Posted by"/"Last updated by" rows, list-page columns, and the values handed to `exportToXlsx` (export should show what the visible column shows). It fetches `/users` once (silently no-ops without `VIEW_USER`) and falls back to the raw username whenever it can't resolve one — not yet loaded, deleted account, or the synthetic `"system"` auditor — so it's always safe to call unconditionally. Deliberately **not** applied to `searchText` functions (the blob the Global Filter searches) — that's a separate, unconfirmed scope; those still key off the raw username.

## Transaction actions & history

**Transaction actions & history** (Inventory Adjustment, Purchase Order/Invoice/Receive, Delivery Receipt, Outlet Receive). Backend: `/transactions/{TYPE}/{id}/history|actions` (see `../Norbiz/docs/TRANSACTION_ACTIONS.md`). Wire with `const activity = useTransactionActivity('<TYPE>', inRecordTab && mode === 'view' ? activeX?.id : null, activeX?.referenceNumber, activeX?.voided)` (`src/hooks/useTransactionActivity.ts`; passing `voided` re-fetches after a void). In view mode, `<TransactionHistory activity={activity} record={activeX} />` (`src/components/TransactionActivity.tsx`) sits at the foot of the `DocSheet` and replaces the old Posted by / Date posted / Voided by `DocSignatures` strip (it falls back to the record's `createdBy/createdAt/voidedBy/voidedAt` when history has no CREATED/VOIDED rows); create mode renders `<TransactionHistory pending />` in the same place. `<TransactionActionsMenu activity={activity} voided={activeX.voided} />` is the first button in `RECORD_ACTIONS` — a dropdown (not one button per action, since actions are company-configured and variable in number) that hides itself when voided or when none of the actions are allowed for the user's roles, shows disabled items with the reason (`Done by you`, `Needs: …`), and owns the `A` hotkey. Taking an action uses `window.prompt` for optional remarks (cancel = abort), then reloads history/actions. The actions themselves are configured on `TransactionActionsPage` (`/transaction-actions`, `MANAGE_TRANSACTION_ACTIONS`, Access Control group): code/name/order/active, allowed roles (checkboxes from `/roles`, so editing roles needs `VIEW_ROLE`), and prerequisites (checkboxes of the other actions with the same company + type; changing company or type clears them). `TRANSACTION_TYPES` in `src/hooks/useTransactionActivity.ts` mirrors the backend `TransactionType` enum by hand — add an entry when the backend adds a type.

## Master-data change history

**Master-data change history.** In view mode, every master-data record sheet (Items, Item Categories, Item Groups, Item SKUs, Brands, Warehouses, Employees, Customers, Suppliers, Users) ends with `<ChangeHistory type="<MASTER_DATA_TYPE>" id={activeX.id} refreshKey={activeX.updatedAt} />` (`src/components/ChangeHistory.tsx`), placed after the Created/Updated `DocSignatures` as the last thing inside `DocSheet`. Backend: `GET /master-data/{type}/{id}/history` (see `../Norbiz/docs/AUDIT.md`), gated by the record's own `VIEW_` permission. It pages 20 at a time newest first ("Load older changes" in the section header), shows UPDATEs as `Field: old → new` (or `<part> added/removed` for an item's SKUs and prices — the backend nets out the delete-and-reinsert and resolves linked records to names), and folds CREATE's initial values into a `<details>`. A change's `label` (sent for parts) wins; otherwise field names are title-cased from the entity field — add an entry to `FIELD_LABELS` when the form caption differs. Empty UPDATEs only come from logs that predate the detailed audit (`detailed: false`). `MasterDataType` mirrors the backend enum by hand.
